1.  What It Is
LMR Capitals is a personal prop-trading journal and performance dashboard for NQ futures (Nasdaq). The user trades multiple funded prop accounts on Tradeify (Select Flex model) and needs to:
Track every trade with full P&amp;L, risk, R:R, session context, and chart screenshots
Journal daily, weekly, and monthly sessions with block editor notes and images
Manage funded account payout cycles (5-day gate, 50% cumulative profit rule)
Distribute trades across accounts via a leader/follower copier with multipliers
Review performance through charts, patterns, drawdown analysis, and AI coaching

1.1  Core Tech
Single file:  index.html (~940KB) — all HTML, CSS, and JavaScript in one file. No React, no Vue, no build step.
Backend:  Supabase (PostgreSQL + Auth + Storage). Project URL: https://agrvylclhvxyevsmmexf.supabase.co
Hosting:  Netlify static site. Site ID: 09e03f83-2353-4a3a-bb21-ae5ab81ef45b. Domain: lmrcapitals.com
Auth:  Supabase Auth (email + password). All tables use RLS — user_id = auth.uid(). Per-user namespaced localStorage keys.

2.  Storage Architecture
Three tiers — Supabase always wins:

Supabase DB  ──(on boot: sbAutoLoadOnStart)──►  In-Memory State  ──(save)──►  localStorage cache
                                                      │
                                    (large blobs)     ▼
                               IndexedDB (chart images)  +  Supabase Storage (receipts, obs screenshots)

▸  Supabase is source of truth.  On every sign-in, all tables are pulled and overwrite the localStorage cache.
▸  Never store base64 in localStorage.  5MB cap. Images go to IndexedDB (trade charts) or Supabase columns (receipts, achievements).
▸  Regression guard in save().  If new state has fewer trades/accounts than the previous save, it merges instead of overwriting — prevents accidental data loss.
▸  Per-user namespace.  On sign-in, _switchUserStore(uid) migrates legacy keys to lmr_v3_state__&lt;uid&gt; and lmr_v3_img__&lt;uid&gt;.
▸  Followers never store trades.  _copierFollowerView(accountId) derives follower trades live from the leader on every render. Zero stored copies.

8.  Payout Rules (Funded Accounts)
8.1  Balance Formula
balance = account.size + SUM(trade.pnl) - SUM(payout.amount)

// NOTE: Payouts are deducted. Withdrawals are NOT (they are the banking side only).
// _accMetrics(account) is the ONLY source of balance — all cards, tiles, and payout
//  calculations call this function. Never compute balance elsewhere.

8.2  Payout Amount
profit  = balance - account.size          // cumulative, not per-cycle
payout  = profit * 0.50                   // 50% — NO 10% fee
payout  = min(payout, account.payoutCap)  // tier cap

// The kept 50% ROLLS FORWARD into the next payout calc.
// Example: earn $1000 → pay $500 → keep $500 → earn $1500 more
//          total profit = $2000 → pay 50% = $1000 → keep $1000

8.3  Eligibility Gate
▸  5 winning days  required since the last payout date. Win threshold by account tier:
50K account  →  day P&amp;L ≥ $150
100K account  →  day P&amp;L ≥ $200
150K account  →  day P&amp;L ≥ $250
▸  Win-day counter  resets after each payout. Profit does NOT reset — it accumulates across cycles.
▸  2nd+ payout  requires positive net profit since the last payout date (cyclePnl &gt; 0).

8.4  Trailing Max Drawdown Floor
floor = min(peak_balance - dd_by_tier, account.size + 100)

// DD by tier: 50K→$2000  100K→$3000  150K→$4500
// Floor locks at (size + $100) once peak is high enough.
// If balance drops below floor → status = &quot;Blown&quot;, blownAt = now
// Blown accounts keep ALL trades and data — only status changes.

8.5  Eval → Funded Auto-Pass
▸  Select track:  profit target ($3,000 for 50K) + ≥3 trading days + best single day ≤ 40% of total profit
▸  Growth track:  profit target + ≥1 trading day (no consistency rule)
▸  Lightning:  funded from day 1, no eval phase
▸  On pass:  mark eval &quot;Passed&quot; (keep data), spawn a FRESH funded account at size (no trades carried over)
▸  Guard:  account.funded_spawned = true prevents double-spawn. Set immediately after creating the funded account.
▸  Trigger:  ONLY in saveTrade() when a trade crosses the profit target. NOT on render.

9.  Copier Model
⚠  This is the most common source of bugs. Get the derived-live model exactly right.

Leader Account  ─── (real trades in Trade Log) ───►  _copierFollowerView(followerId)
                                                             │
                                                    filter: date &gt;= _folSince(acc, cfg)
                                                    scale:  trade.pnl * cfg.multiplier
                                                    id:     &quot;d-&lt;accId&gt;-&lt;leaderId&gt;&quot;
                                                             │
                                                    Follower A  +  Follower B  +  …

9.1  Core Rules
▸  Followers NEVER store trades.  _copierFollowerView() derives the follower&apos;s list live on every render. Zero DB writes for followers.
▸  Date scoping via _folSince(acc, cfg):  priority = acc.startDate → cfg.connectedAt → acc.date. A new follower only gets leader trades from its start date.
▸  Self-healing:  _copierPurgeFollowerStored() runs every renderAccountCards() and deletes any stray stored copies on connected followers.

9.2  P&amp;L Display Rules
▸  Dashboard / sidebar Total P&amp;L  = de-duped leader trades only. Never summed across copier accounts.
▸  Daily heatmap  = de-duped daily P&amp;L × _cockpitCountOn(day) = leader(1) + Σ multipliers of active followers that day.
▸  Per-account view  = that account&apos;s own derived trades only.
▸  _accMetrics(account)  = size + Σ trade P&amp;L − Σ payouts. Single source of truth for any account&apos;s balance.

9.3  Clicking a Follower Trade
Calls goToTradeInLog(id) → _originTradeId(id) → resolves synthetic id back to the real leader trade id → navigates to it in the Trade Log journal. Never opens a separate modal.

10.  Week / Month Boundary Rule
⚠  A &quot;most weekdays&quot; rule was tried and reverted — it hid June&apos;s W5. The Monday rule is final.

▸  A week belongs to its Monday&apos;s month.  Cross-month weeks are NEVER split.
Example:  Mon Jun 29 → Fri Jul 3 2026 is June&apos;s W5. Trades on Jul 1–3 count in June&apos;s monthly P&amp;L. July W1 starts Mon Jul 6.

10.1  Canonical Functions
_weekMondayStr(dateStr)          → Monday date of that week
_weekOwnerMonth(mondayStr)       → mondayStr.slice(0,7)  // YYYY-MM of the Monday — THE rule
_ownedWeeksOfMonth(ym)           → chronological week list { num, monDate, label }
getWeeklyKeyForDate(date)        → &quot;YYYY-MM-Wn&quot;  via the above
computeWeekPnl(weekKey)          → sum trade P&amp;L for that week (excl. mirror copies)
computeMonthPnl(monthKey)        → sum trade P&amp;L for that month (excl. mirror copies)

▸  All P&amp;L and journal code  must key off getWeeklyKeyForDate / _weekOwnerMonth. Never re-derive week numbers from the calendar month.
▸  State data is never lost  by boundary rule changes — weekly keys just get remapped. Data is preserved under the new key.
